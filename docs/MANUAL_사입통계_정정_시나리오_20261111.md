# 사입 통계 · 판매 정정 업무 매뉴얼 (가상 시나리오판)

> 목적: 새로 만든 기능으로 할 수 있는 업무를 가상의 하루·한 달 이야기로 따라가며, **이상하거나 빠진 부분을 찾아내기 위한** 문서다.
> 모든 바코드·금액·날짜는 가상이다(실제 데이터 아님). 공개 저장소 문서이므로 실제 원가·바코드를 적지 않는다.
> 각 기능 앞의 상태 표시: **[사용 중]** 운영 반영 완료 / **[적용 대기]** 만들어 검증했고 운영 적용 승인 대기 / **[설계]** 설계만 있고 아직 없음.

## 1. 새 사입이 들어왔다 — 차시 만들기부터 회수율까지 [사용 중]

**상황:** 11월 초 유어스업에서 옷 120벌과 모자 10개를 사 왔다. 가상의 "유어스업 9차".

1. **차시 만들기 (김민지)** 허브 홈 → 분석 도구 → 사입 통계 → **차시** 탭 → **＋ 새 차시**.
   - 출처 `유어스업` 선택 → 차시 번호가 `9`로 제안된다(마지막 차시 + 1).
   - 입고일은 세탁·검수가 이틀에 걸치면 시작일~끝일을 둘 다 넣는다. 사입 총액은 정산 전이면 비워 둔다.
   - 부가세 포함 체크: 반문화·윤관호는 자동으로 꺼져 있다.
   - **만들기**를 누르면 "9차" 안에 **의류**와 **잡화** 두 칸이 한꺼번에 생긴다.
2. **입고 (직원)** 신규 입고 → 세션 → **행거 추가** → 출처 `유어스업` 선택 → **차시** 칸이 나타난다 → `9차` 선택.
   - 의류 행거도 모자 행거도 똑같이 `9차`를 고른다. 의류인지 잡화인지는 직원이 고르지 않는다.
3. **승인 (바코드 발급)** 바코드가 발급되는 순간 각 물건이 차시에 등록된다. 카테고리가 `자켓`이면 9차 의류, `모자`면 9차 잡화, `봉투`는 집계에서 빠진다.
   - 그 순간의 가격이 **최초 프라이싱**으로 고정된다(이후 가격을 바꿔도 원가 안분은 안 변함).
4. **확인** 사입 통계 → 차시 → 유어스업 → `9차`를 펼친다. 의류 120벌 / 잡화 10개로 나뉘어 있고 카테고리 표가 나온다. 사입 총액이 없으니 "원가 미입력" 표시가 붙는다.
5. **사입 총액 입력 (정산 후)** 9차 → 의류 **원가·정보 수정** → 사입 총액 입력 → 저장. 잡화도 같은 방식으로 따로 입력한다.
   - 저장하면 물건별 원가가 `최초 프라이싱 × 총액 ÷ 최초 프라이싱 합`으로 자동 안분되고 회수율이 나온다.
6. **끝났을 때** 판매가 충분히 끝나면 **원가·정보 수정**에서 "종료"를 체크한다. 종료하면 입고 화면의 차시 선택 목록에서 사라진다.

**이 시나리오에서 살펴볼 점**
- 차시를 만들기 **전에** 입고를 하면 차시 선택란이 안 나오고, 그 물건은 차시 없이 들어간다(→ 2번 시나리오). **운영 규칙: 새 사입은 차시를 먼저 만들고 입고한다.**
- 입고 때 차시를 **잘못 골랐을 때** 고치는 화면이 없다. 드문 일이라 만들지 않고, 생기면 SQL로 고친다(황태훈 + 사입이관 세션).
- 승인 뒤에는 행거의 차시를 바꿀 방법이 없다(위와 같음).
- 수선·지연으로 일부가 늦게 입고되는 경우: 차시를 **종료하지 않고 열어 두면** 늦게 온 물건도 같은 차시를 골라 입고할 수 있다. 끝난 차시는 종료해야 목록이 헷갈리지 않는다.

## 2. 차시 없이 들어간 물건 [운영 규칙: 차시를 먼저 만든다]

**상황(실제 사례, 2026-11-09):** 유어스업 모자 83개를 차시를 만들기 전에 입고해 점검 탭에 쌓였다.

1. 사입 통계 → **점검** 탭 → "차시 미배정 사입 물건"에 바코드·출처·카테고리·가격·등록일이 나온다(발견 전용).
2. 이번에는 사후 배정 기능을 만들지 않고 **한 번만 SQL로 수동 처리**했다(`scripts/purchase-batch-cr8-20261111.sql`: 8차 생성 + 83개 편입). 모자는 카테고리로 잡화 차시(`CR8_E`)에 들어갔다.
3. 앞으로는 **새 차시를 먼저 만들고 신규 입고를 잡는다.** 점검의 "차시 미배정"은 누가 빼먹었을 때 발견하는 안전장치로 남긴다.

**살펴볼 점:** 입고 먼저·차시 나중 흐름(입고일을 미리 알 수 없는 경우)은 지원하지 않는다. 필요해지면 점검 탭에 "차시 배정" 기능을 만든다(이때 최초 프라이싱 = 입고 직후 가격, 가격 수정 이력이 있으면 첫 수정 전 가격).

## 3. 에코옥션과 야후옥션이 한 차시로 합쳐 들어왔다 [사용 중]

**상황:** 타카미가 두 경매 물건을 합쳐서 보냈다. 가상의 "에코옥션 2026년 7차"(158벌 중 야후옥션 물건 10벌). 사입 총액은 합쳐서 한 번에 지급했다.

1. 차시 만들기: 대표 출처 `에코옥션`으로 만든다(번호 제안은 `2607`).
2. 입고에서 에코옥션 행거는 `에코옥션 차시` 아래 `2026년 7차`를 고른다. **야후옥션 행거**는 출처를 `야후옥션`으로 고르고, 차시 목록의 **"다른 출처 차시 (한 차시로 합쳐 들어온 경우)"** 아래에서 `에코옥션 · 2026년 7차`를 고른다.
3. 사입 통계 → 차시 → 에코옥션 → 2026년 7차를 펼치면 카테고리 표 아래 **"출처 구성"** 표가 나온다: 에코옥션 148 / 야후옥션 10, 출처별 판매·판매액·안분 원가·회수율.
4. 요약·출처 탭의 숫자는 모두 에코옥션으로 잡힌다. 야후옥션 개별 회수율은 "추정치"로만 보인다(원가를 합쳐서 줬기 때문).

**살펴볼 점**
- "다른 출처 차시" 목록에는 에코옥션·야후옥션뿐 아니라 **유어스업 진행 중 차시도** 나온다. 직원이 잘못 고를 수 있다(경매 두 곳끼리만 묶이도록 제한하는 안이 있음).
- 야후옥션 물건의 출처가 틀렸을 때 고칠 방법이 없다(→ 8번 시나리오).

## 4. 월요일 아침 보고 [사용 중]

**상황:** 매주 월요일 아침 이사님께 사입 현황을 보고한다.

1. **07:40** 서버가 자동으로 출처별 숫자를 스냅샷으로 저장한다(보고일 = 월요일, 집계 = 일요일까지의 판매).
2. **08:00** 서버가 엑셀(출처별·차시별·카테고리·출처구성 4개 시트)을 만들어 Slack 채널에 올린다. 성공·실패는 텔레그램으로 온다.
3. 허브에서 → **주간 보고** 탭: 보고일별 표(회수율·판매총액·입고 원가·판매이익·남은 재고 원가·프라이싱 기준 판매비율 중 선택). **출처** 탭: 한 출처의 회수율 추이 그래프와 차시별 막대.
4. 자동 저장이 실패한 주에는 김민지·황태훈이 **오늘 스냅샷 저장** 버튼으로 직접 저장한다. 같은 날짜는 덮어쓴다.

**살펴볼 점**
- 스냅샷은 지울 수 없다(잘못 저장해도 같은 보고일을 덮어써야 한다).
- 화면의 "기준" 날짜를 바꿔 조회해도 스냅샷에는 영향이 없다. 화면 기본값은 **어제**까지이고 스냅샷은 **일요일**까지라서 월요일에 화면 숫자와 보고서 숫자가 하루 차이 날 수 있다.

## 5. 폐기 물건 처리 [사용 중]

**상황:** 매장에서 수선이 불가능한 옷 3벌을 폐기하기로 했다.

1. 이동 앱에서 대상 물건을 `폐기` 위치로 이동 → 승인(22:00 자동) → VM이 DB 위치를 바꾼다.
2. **DB가 자동으로** 그 물건의 상태를 `폐기(disposed)`로 바꾼다(사람이 따로 할 일 없음).
3. 사입 통계에서 그 물건은 입고 수량·프라이싱 합에서 빠지고, **원가는 입고 원가에 남는다**(폐기 손실). 화면의 "폐기 포함" 체크를 켜면 엑셀과 같은 숫자로 볼 수 있다.
4. 통합 물건 조회에서는 기본값(보유중만)에 안 나오고, **폐기만** 또는 **전체**를 고르면 보인다.
5. 폐기에서 다른 위치로 이동하면 자동으로 재고로 되돌아온다.

**살펴볼 점**
- 이동 신청부터 상태가 바뀔 때까지 최대 하루가 걸린다(승인이 22:00).
- 판매된 물건이 폐기 위치에 있으면 판매 상태가 유지된다.

## 6. 판매 기록이 잘못 들어왔다 — 정정하기 [적용 대기: SQL·화면 모두 만듦]

> 아래는 **1단계 SQL이 운영에 적용된다는 가정**의 이야기다. 화면은 홈 → 분석 도구 → **정정 · 이력**(`correction/`)이고, 사입 통계 점검 탭의 "재고에 없는 바코드의 판매" 항목에서 **정정하기** 링크로 바로 열린다. 바코드를 입력해 판매 기록을 찾고, 행마다 **바코드 정정** / **판매 제외**를 고른 뒤 사유를 적고 실행한다(실행 전 확인창).

### 6-1. 바코드 오타 (현금 판매)
- **상황:** 7월 28일 성수에서 현금으로 판 물건을 직원이 현금매출 시트에 `CR0347`로 잘못 적었다. 실제 바코드는 `CR03347`. 다음 날 시트와 엑셀은 고쳤는데 허브 DB에는 오타가 남았다.
- **증상:** 사입 통계 점검에 "재고에 없는 바코드의 판매 `CR0347`"이 뜬다. 진짜 물건 `CR03347`은 계속 재고로 남아 있다.
- **정정:** 판매 정정(원래 바코드 `CR0347`, 판매일 7/28, 정정 바코드 `CR03347`, 사유 "현금매출 시트 입력 오타").
- **결과:** 판매 행이 `CR03347`로 옮겨지고 재고 상태가 `판매됨`이 된다. 이력에 정정 전 값(원래 판매 행, 재고 상태)이 남는다. 다음 날 점검 탭에서 그 항목이 사라진다.

### 6-2. 택갈이
- **상황:** 손님이 비싼 옷(`BX-2001`, 228,000원)의 택을 싼 옷(`BX-9001`, 168,000원)의 택으로 바꿔 달아 168,000원에 샀다. 엑셀에는 택 바코드 `BX-9001`로 기록됐다.
- **정정:** 원래 `BX-9001` → 정정 `BX-2001`, 판매 가격 168,000원 유지, 사유 "택갈이 사건".
- **결과:** 실제 팔린 `BX-2001`이 `판매됨`, 택 물건 `BX-9001`은 `재고`로 돌아온다. 사입 통계에서 판매가 `BX-2001`이 속한 차시로 옮겨 간다.
- **재동기화를 해도:** 서버가 나중에 같은 날짜를 다시 읽어 `BX-9001`을 다시 넣으려 해도, DB가 정정 이력을 보고 `BX-2001`로 바꿔 받는다. 택 물건 재고가 다시 `판매됨`으로 바뀌는 것도 막는다.
- **물건 현재가:** 정정이 바꾸는 건 판매 가격뿐이다. 물건 자체의 가격을 바꾸려면 가격 수정 앱에서 따로 해야 한다.

### 6-3. 판매 제외 (중복결제·반품)
- **상황:** 손님 카드가 두 번 결제돼 같은 바코드의 판매가 중복으로 들어왔다(한 줄에 합계 금액이 들어옴).
- **정정:** 판매 제외(바코드, 판매일, 사유 "중복결제, 1회분 환불", 재고 복구 여부 선택).
- **결과:** 판매 행이 삭제되고 이력에 남는다. 재고 복구를 켜면 그 물건이 다시 재고가 된다. 같은 날짜를 재동기화해도 이 판매는 다시 들어오지 않는다.

### 6-4. 정정할 수 없는 경우
- 환불 기록이 있는 판매 행은 정정이 거부된다("환불 기록이 있는 판매는 정정할 수 없어요").
- 정정하려는 바코드가 재고에 없거나, 이미 판매 기록이 있는 바코드면 거부된다.
- 사유가 비어 있으면 거부된다. 권한이 없으면 거부된다.

### 6-5. 이력 보기
- 로그인한 직원은 누구나 정정 이력을 볼 수 있다: 종류, 원래·정정 바코드, 판매일, 사유, 처리자, 시각, 바꾸기 전 값. 수정·삭제는 아무도 못 한다.

**살펴볼 점**
- 화면은 만들어 둠(`correction/`). 권한이 없는 직원은 입력이 숨겨지고 이력만 보인다.
- 환불이 얽힌 판매는 **거부만** 하고, 설계에서 정한 "환불·재판매를 이력에 기록하는" 경로는 만들지 않았다. 환불 후 재판매를 어떻게 처리할지 비어 있다.
- 엑셀 `전매장매출` 시트는 오타 그대로 남는다(DB만 맞음).
- 정정은 한 단계만 따라간다. 정정한 바코드를 다시 정정하면 마지막 이력만 쓴다.
- 임시로 만든 사입 통계의 제외 장치(`purchase_sale_exclusions`)와 이 기능이 두 갈래로 남는다.

## 7. 점검 탭에서 확인 끝낸 항목 숨기기 [설계: 구현 전]

- **상황:** 점검 탭에 에코옥션 옛 물건 `N-6254`가 "차시 미배정"으로 계속 뜬다. 사입 통계 대상이 아니라고 확인이 끝난 물건이다.
- **하는 일:** 항목 옆 **확인함**을 누른다 → 누가 언제 눌렀는지 기록되고 목록에서 사라진다. 숨긴 항목만 따로 모아 볼 수 있고 **확인 취소**로 다시 띄울 수 있다.
- **살펴볼 점:** 누르는 권한을 누구에게 줄지 정해야 한다(김민지·황태훈? 정정 권한자 3명?).

## 8. 입고 때 출처를 잘못 골랐다 — 출처 수정 [설계]

- **상황:** 에코옥션 물건인데 입고 때 런드리고로 골랐다. 지금은 허브에서 고칠 방법이 없어 드롭박스 엑셀만 손으로 고쳐서 DB와 어긋났다(실제로 7건 있었음).
- **설계:** **출처 수정**(바코드, 새 출처, 사유) → DB가 바뀌고 이력이 남는다 → **반영 큐**에 "엑셀 입고시트 출처 칸을 에코옥션으로"가 쌓이고 → 서버가 몇 분 안에 엑셀에 써 준다. 실패하면 텔레그램으로 알린다.
- 사입 통계의 "출처 구성"은 이 값을 읽어서 자동으로 맞춰진다.

**살펴볼 점**
- 사람이 드롭박스 엑셀을 직접 고치는 것은 허브로 막을 수 없다(드롭박스 권한 문제로 따로 논의 중).
- 이동(위치 변경)은 기존 이동 세션, 출처·비고는 이 큐 — 두 갈래가 생긴다.

## 9. 택분실 물건 [짝 맞추기·교환은 하지 않기로 함 — 2026-11-11 사용자 결정]

- 택 없는 옷은 지금처럼 **신규 입고(출처 `택분실`, A/U 바코드)** 로 다시 잡는다. 입고 때 사진을 남기므로 앞으로 택분실 입고 자체가 줄어든다.
- 재고조사에서 안 나온 물건(미스캔)은 **있는 그대로** 본다. 결과 화면에서 처리 방법은 **찾음 / 미확인 위치로 이동 / 선택한 물건 폐기** 셋이다.
- 판단할 때는 지난 조사~이번 조사 사이에 출처가 `택분실`인 입고가 몇 개였는지를 사람이 참고한다(출처가 `택분실`인 물건 목록은 DB에서 바로 조회).
- 추측으로 원 바코드와 짝을 맺지 않는다(100% 확실하지 않으면 위험). 따라서 교환·교환 취소·복원 기능과 연결 컬럼은 만들지 않는다.
- 사입 통계에서 `택분실` 출처 물건은 추적 대상이 아니다.
